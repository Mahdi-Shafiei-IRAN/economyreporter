# نقشه‌ی راه

> فلسفه: به‌جای «همه‌ی لایه‌ها را بساز»، اول یک **برش عمودی نازک** که ثابت کند قلب سیستم (پیامک → تراکنش → نمایش) کار می‌کند؛ بعد لایه‌های خانواده/سرور/sync را دور آن بساز.

## فاز −۱ — جمع‌آوری نمونه‌ی پیامک
مقدم بر هر کدی. جزئیات در [sms-parsing.md §۱](sms-parsing.md#۱-اول-از-همه-جمعآوری-نمونهی-واقعی).
- **خروجی:** پوشه‌ی `mobile/test/fixtures/sms/` با ۵۰–۱۰۰ نمونه‌ی برچسب‌خورده.

## فاز ۰ — Feasibility Spike
کوچک‌ترین اپ ممکن که فقط ثابت کند:
```text
گوشی هدف → دریافت پیامک واقعی بانک → خواندن متن → نمایش پارس‌شده
```
- **هدف بازتعریف‌شده:** نه «آیا Play اجازه می‌دهد» بلکه «آیا روی گوشی‌های واقعی خانواده (نصب مستقیم/بازار) پیامک درست خوانده می‌شود». (چرا: [sms-parsing.md §۶](sms-parsing.md#۶-خواندن-پیامک-روی-android--واقعیت-انتشار).)
- اگر این جواب نداد، کل طراحی SMS-محور باید بازنگری شود (مثلاً به سمت NotificationListener).

## فاز ۱ — برش عمودی نازک ⭐ نقطه‌ی شروع واقعی محصول
یک بانک، یک گوشی، کاملاً آفلاین:
```text
پیامک واقعی → نرمال‌سازی ارقام → پارسر همان بانک → SQLite → لیست تراکنش → جمع درآمد/هزینه
```
- **خروجی:** اپی که همین حالا برای خودت مفید است، حتی بدون سرور.
- این «قلب» است؛ وقتی کار کرد، بقیه دور آن ساخته می‌شود.

## فاز ۲ — پایه‌ی بک‌اند
```text
Django · DRF · PostgreSQL · JWT · Custom User · FamilyGroup · Membership (سقف ۳)
```
- سرور روی کامپیوتر خودت اجرا می‌شود ([dev-setup.md](dev-setup.md)).
- **خروجی:** `/register`، `/login`، `/me`، `/family`.

## فاز ۳ — مدل داده‌ی اصلی
مدل‌های [architecture.md §۴](architecture.md#۴-مدل-دادهی-سرور) با UUID، سه زمان، ایندکس‌ها، constraintها.
- شامل افزوده‌های حیاتی: `kind=transfer`، `amount_rial`، `balance_after_rial`، `counterparty`.

## فاز ۴ — CRUD API
Auth · Family · Account · Card · Category · Budget · Transaction API.
- **هنوز SMS وارد نمی‌شود.**
- **Authorization سطح‌شیء** روی همه: هر منبع فقط برای خانواده‌ی صاحبش.

## فاز ۵ — پایه‌ی Flutter
```text
Login · Dashboard shell · Navigation · SQLite · Repository layer · API client · Secure storage
```
معماری لایه‌ای؛ UI هرگز مستقیم با SQLite کار نمی‌کند.

## فاز ۶ — موتور تراکنش محلی
اول تراکنش دستی، قبل از اتصال SMS:
```text
ثبت → SQLite → pending ؛ سپس ویرایش/حذف/فیلتر/جستجو + صف بازبینی (needs_review)
```

## فاز ۷ — پارسر کامل SMS
```text
SMS Receiver · تشخیص بانک · نرمال‌سازی · پارسر per-bank · سازنده‌ی تراکنش · قواعد دسته
```
- تست رگرسیون روی کل corpus فاز −۱ (جزئیات: [sms-parsing.md §۵](sms-parsing.md#۵-تستهای-الزامی-پارسر)).

## فاز ۸ — Background Sync
```text
تشخیص شبکه · Background worker · Outbox · آپلود دسته‌ای (تا ۵۰ تایی) · Retry · Backoff · Idempotency
```
- backoff: `۳۰ثانیه → ۲دقیقه → ۱۰دقیقه → ۳۰دقیقه`.

## فاز ۹ — داشبورد خانواده
```text
جمع درآمد/هزینه/مانده · هزینه‌ی هر عضو · تفکیک دسته · مصرف هر کارت · روند ماهانه · تطبیق مانده
```
- transferها از جمع درآمد/هزینه کنار گذاشته می‌شوند.

## فاز ۱۰ — Conflict & Recovery
همه‌ی این سناریوها تست شوند:
```text
قطع شبکه · کیل‌شدن اپ · ری‌استارت گوشی · سرور در دسترس نیست
تکرار sync · شکست بخشی از batch · انقضای JWT · migration پایگاه داده
```
**مهم‌ترین تست sync:**
```text
۱ تراکنش محلی بساز → اینترنت نباشد → ۹ تای دیگر بساز → اینترنت برگردد → sync
→ وسط sync اپ را کیل کن → ری‌استارت → دوباره sync
→ سرور باید دقیقاً ۱۰ تا داشته باشد، نه ۲۰ تا.
```

## فاز ۱۱ — سخت‌سازی امنیت
```text
Authentication · Authorization · Token در Keystore · رمزنگاری SQLite · HTTPS
Rate limiting · جلوگیری از نشت داده (حتی لاگ‌نکردن متن کامل SMS)
```

## فاز ۱۲ — تولید
```text
مهاجرت به VPS ایرانی · HTTPS (Caddy/Nginx) · دامنه‌ی .ir · بکاپ · Health check · مانیتورینگ
```
بعداً در صورت نیاز: Redis · Celery · Sentry.
