# طرحِ نسخه‌ی ۲: دفترِ حساب با تأییدِ کاربر

> وضعیت: **مصوب** (۱۴۰۵/۰۷/۰۳) — مرجعِ پیاده‌سازی. هر جا کد با این سند فرق داشت، این سند درست است
> مگر کاربر خلافش را بگوید. نسخه‌ی ۱ از این به بعد **منجمد** است: فقط رفعِ باگِ بحرانی، بدونِ قابلیتِ تازه.

## ۱. چرا نسخه‌ی ۲

نسخه‌ی ۱ سعی می‌کرد همه‌چیز را **خودکار و بی‌صدا** حدس بزند: پیامک را خودش ثبت می‌کرد، خودش حذف
می‌کرد (قانون/تعمیر)، خودش برمی‌گرداند (برگشتِ خودکار، اثبات با مانده)، خودش به حساب وصل می‌کرد
(نام مستعار، سنجاق)، و با هر تغییرِ پارسر **کلِ تاریخچه‌ی پیامک‌ها** را دوباره پردازش می‌کرد. هر لایه برای
یک ایرادِ واقعی اضافه شد، ولی لایه‌ها با هم تداخل دارند و یک ردیف می‌تواند هم‌زمان «از سرور آمده، بی‌شماره،
حذف‌شده روی نصبِ قبلی، دوباره خوانده‌شده» باشد. نتیجه: عددهایی که کاربر نمی‌فهمد از کجا آمده‌اند و با
نصبِ دوباره خراب می‌شوند (مثال: ملتِ کاربرِ دوم). حدود ۶ هزار خط از ۱۹ هزار خطِ اپ فقط همین حدس‌ها و
وصله‌هاست و ۲۴ تنظیمِ پنهان حالت را نگه می‌دارند.

نسخه‌ی ۲ همان ظاهر، ورود، خانواده، دسته‌ها، بودجه و به‌روزرسانی را نگه می‌دارد ولی **هسته** را عوض می‌کند.

## ۲. تصمیم‌های کاربر (قطعی)

| # | تصمیم |
|---|---|
| ت۱ | **تاریخِ شروع = اولِ ماهِ شمسیِ جاری** (در اولین اجرای نسخه‌ی ۲). پیامکِ قبل از آن کلاً نادیده. تاریخِ شروع روی سرور هم ذخیره می‌شود تا نصبِ دوباره (حتی ماهِ بعد) همان را برگرداند. |
| ت۲ | **هیچ پیامکی خودکار ثبت نمی‌شود.** هر پیامکِ بانک «منتظرِ تأیید» می‌ماند تا کاربر ثبت یا ردش کند. برنامه فقط **پیشنهاد** می‌دهد. |
| ت۳ | **نصبِ دوباره و به‌روزرسانی هیچ چیزی را خراب نمی‌کند.** هر تصمیمِ کاربر روی سرور است و بعد از نصبِ دوباره عیناً برمی‌گردد. |
| ت۴ | **موجودیِ الانِ هر حساب مبناست.** جمع و تفریق از همین عدد حساب می‌شود و هر جا تراکنش‌ها با موجودی نخوانند (حتی ورودِ دستیِ اشتباه) «اختلاف» نشان داده می‌شود. |

## ۳. قانون‌های تغییرناپذیر (Invariants)

هر کدِ نسخه‌ی ۲ باید این‌ها را حفظ کند و برای هر کدام تست باشد:

- **I1 — فقط کاربر می‌نویسد:** هیچ تراکنشی ساخته، عوض یا حذف نمی‌شود مگر با کارِ صریحِ کاربر (یا همگام‌سازیِ
  کارِ صریحِ همان کاربر از گوشیِ دیگرش). هیچ «تعمیرِ خودکار»، «برگرداندنِ خودکار» یا «یکی‌کردنِ خودکار» نیست.
- **I2 — تصمیم قطعی است:** تصمیمِ کاربر روی یک پیامک (ثبت/رد) هرگز خودکار عوض نمی‌شود؛ بهترشدنِ پارسر فقط
  پیشنهادِ پیامک‌های **منتظر** را عوض می‌کند.
- **I3 — هر عدد قابلِ توضیح است:** موجودیِ هر حساب = آخرین «نقطه‌ی مانده» + تراکنش‌های بعد از آن؛ هر عددِ
  روی صفحه با یک فهرستِ مشخص از تراکنش‌ها و نقطه‌ها توضیح داده می‌شود.
- **I4 — قبل از تاریخِ شروع وجود ندارد:** هیچ پیامک یا تراکنشی قبل از تاریخِ شروع روی هیچ عددی اثر ندارد.
- **I5 — نصبِ دوباره = همان وضعیت:** بعد از حذف و نصبِ دوباره، حساب‌ها، تراکنش‌ها، تصمیم‌ها و تاریخِ شروع
  عیناً همان است؛ فقط پیامک‌هایی که تصمیم ندارند «منتظر» می‌شوند.
- **I6 — حریمِ خصوصی:** متنِ خامِ پیامک هرگز از گوشی بیرون نمی‌رود و لاگ نمی‌شود (قانونِ CLAUDE.md).

## ۴. مفاهیم

### ۴.۱ حساب (Account)
کارت یا حسابِ بانکیِ یک نفر (یا «نقد» / حسابِ بی‌پیامک). همان «کیف» (`wallets`) با چند ستونِ تازه.

| فیلد | توضیح |
|---|---|
| `id` | UUID ساخته‌شده روی گوشی |
| `owner_user_id`, `owner_name` | صاحب |
| `bank_id` | از رجیستریِ بانک‌ها؛ برای «نقد» null |
| `label` | «ملت حقوق»، … |
| `card_last4` (چند مقدار) / `account_ref` | برای **پیشنهادِ** حسابِ پیامک. روی سرور هم هست (همین امروز کیف‌ها sync می‌شوند) تا نصبِ دوباره کار کند. |
| `archived` | حسابِ کنارگذاشته |

### ۴.۲ نقطه‌ی مانده (Checkpoint)
یک موجودیِ **قطعی** در یک لحظه. دو منبع دارد:
1. **دستی (لنگر):** «موجودیِ الان» که کاربر هنگامِ ساختِ حساب یا در «تطبیق با موجودیِ واقعی» وارد می‌کند.
2. **بانک:** مانده‌ی داخلِ پیامکی که کاربر **ثبت کرده** (`bank_balance_after` همان تراکنش).

جدولِ `checkpoints`: `id, account_id, at, balance_rial, source('manual'|'sms'), entry_id?, note, created_at, updated_at, deleted_at`.
(نقطه‌ی بانکی **ذخیره نمی‌شود**: همان `bank_balance_after` تراکنشِ ثبت‌شده است و با ویرایش/حذفِ تراکنش خودبه‌خود
عوض می‌شود؛ جدولِ `ledger_checkpoints` فقط نقطه‌های دستی را دارد و کاربر ویرایش یا حذفشان می‌کند.)

### ۴.۳ تراکنشِ دفتر (Entry)
فقط با کارِ کاربر ساخته می‌شود: ثبتِ یک پیامک، افزودنِ دستی، یا «اصلاحِ اختلاف».

| فیلد | توضیح |
|---|---|
| `id` | UUID |
| `account_id` | حتماً یک حساب دارد (تراکنشِ بی‌حساب نداریم) |
| `kind` | `income` / `expense` |
| `is_transfer` | انتقال بینِ حساب‌های خودِ خانواده: موجودی را عوض می‌کند ولی در درآمد/هزینه نیست. `transfer_pair_id` دو طرف را به هم وصل می‌کند. |
| `amount_rial` | مثبت |
| `occurred_at` | زمانِ رخداد (ساعت/دقیقه) |
| `bank_balance_after` | مانده‌ی بانک بعد از همین تراکنش، اگر پیامک داشت (→ نقطه‌ی مانده‌ی بانکی) |
| `source` | `sms` / `manual` / `adjustment` |
| `sms_key` | کلیدِ پیامکِ منبع (بخش ۵.۲)؛ برای دستی null |
| `note`, دسته‌ها (`entry_categories`) | |
| `created_by_device`, `created_at`, `updated_at`, `deleted_at` | حذف نرم؛ فقط با کارِ کاربر |

### ۴.۴ پیامکِ ورودی (SmsItem)
هر پیامکِ **فرستنده‌ی مجاز** که بعد از تاریخِ شروع رسیده، یک ردیف در `sms_items`:

| فیلد | توضیح |
|---|---|
| `key` | کلیدِ پایدار (بخش ۵.۲) — یکتا |
| `sender`, `received_at`, `body` | **متن فقط روی گوشی** |
| پیشنهاد | `sugg_kind, sugg_amount, sugg_balance, sugg_occurred_at, sugg_account_id, sugg_reason` — خروجیِ پارسر؛ فقط پیشنهاد |
| `status` | `pending` / `accepted` / `rejected` |
| `entry_id` | اگر ثبت شد |
| `reject_reason` | `not_tx` (رمز/تبلیغ/اعتبار)، `duplicate`، `other` |
| `decided_at`, `parser_version` | |

`status` و `entry_id` و `reject_reason` = **تصمیم**؛ فقط کاربر عوضشان می‌کند (I2). ستون‌های پیشنهاد را پارسرِ
تازه‌تر فقط برای `pending` بازنویسی می‌کند.

**جهتِ کارت‌به‌کارت/حواله:** پارسر برای این‌ها نوعِ `transfer` بدونِ جهت می‌دهد (نسخه‌ی ۱ آن‌ها را در موجودی
**صفر** می‌شمرد — یکی از علت‌های ناجوریِ زنجیره). در نسخه‌ی ۲ جهت از اختلافِ مانده با نقطه‌ی قبلیِ همان حساب
پیشنهاد می‌شود (`مانده − قبلی = +مبلغ` ← واریز، `−مبلغ` ← برداشت)؛ اگر نشد، `sugg_kind = null` («جهت معلوم
نیست») و کاربر هنگامِ ثبت انتخاب می‌کند. تراکنشِ دفتر همیشه `income` یا `expense` است؛ `is_transfer` جداست.

## ۵. جریانِ پیامک

### ۵.۱ از رسیدن تا دفتر
```
پیامکِ بانک (زنده یا صندوق) ──► فرستنده مجاز است؟ ──نه──► نادیده
                                  │بله
                                  ▼
                   رسیده بعد از تاریخِ شروع؟ ──نه──► نادیده (I4)
                                  │بله
                                  ▼
          کلید (۵.۲) قبلاً هست؟ ──بله──► فقط متن/زمان را تکمیل کن (اگر خالی)؛ تصمیم دست‌نخورده
                                  │نه
                                  ▼
          تصمیمِ همین کلید روی سرور هست؟ ──بله──► همان تصمیم (نصبِ دوباره؛ I5)
                                  │نه
                                  ▼
            پارس ← پیشنهاد (حساب/نوع/مبلغ/زمان/مانده) ← status = pending
                                  ▼
          نوتیفیکیشن: «ملت: برداشت ۱٬۲۵۰٬۰۰۰ — [ثبت] [تراکنش نیست]»
```
- **دریافتِ زنده** فقط یک ردیفِ `pending` می‌سازد (یا خواندنِ صندوق را چند ثانیه بعد صدا می‌زند)؛ هرگز
  مستقیم تراکنش نمی‌سازد.
- **باز شدنِ اپ:** صندوق از `max(تاریخِ شروع، آخرین خواندن − ۲ روز)` خوانده می‌شود.
- پیامک‌های قبل از تاریخِ شروع حتی در `sms_items` هم نمی‌آیند.

### ۵.۲ کلیدِ پایدارِ پیامک (ضدتکرار)
`content_hash = sha256(canonicalSender | normalizeForParsing(body))` و `received_at`.
دو پیامک یکی‌اند اگر `content_hash` برابر و فاصله‌ی `received_at` ≤ ۱۰ دقیقه باشد (زمانِ دریافتِ زنده و
ستونِ `date` صندوق چند ثانیه تا چند دقیقه فرق دارند؛ کلیدِ ۵ دقیقه‌ای نسخه‌ی ۱ همین را خراب می‌کرد).
`key` = `content_hash:received_at_minute` اولین نسخه‌ای که دیده شد؛ تطبیق همیشه با قاعده‌ی ۱۰ دقیقه.
- بانک همان متن را **دوباره** بفرستد (بیش از ۱۰ دقیقه بعد) → پیامکِ جدا، ولی پیشنهادش «احتمالاً تکراری»
  (بخش ۶.۶) — تصمیم با کاربر.
- نرمال‌سازی برای پارس (`cleanForParsing`) با نرمال‌سازیِ کلید یکی **نیست**؛ کلید هرگز با بهترشدنِ پارسر عوض
  نمی‌شود.

### ۵.۳ پیشنهادِ حساب
به ترتیب: (۱) شماره‌ی کارت/حسابِ داخلِ پیامک با حساب‌های تعریف‌شده؛ (۲) بانک فقط **یک** حساب دارد؛
(۳) مانده‌ی پیامک دقیقاً با زنجیره‌ی یک حساب جور است (منطقِ `proveByBalance` نسخه‌ی ۱، حالا فقط پیشنهاد)؛
وگرنه خالی و کاربر انتخاب می‌کند. شماره‌ی ناشناخته → «این حسابِ تازه است؟ [بساز]».

## ۶. موجودی و اختلاف (پاسخِ ت۴)

### ۶.۱ موجودیِ حساب
```
C = آخرین نقطه‌ی مانده‌ی حساب (دستی یا بانکی)
موجودی = C.balance + Σ علامت‌دارِ تراکنش‌های بعد از C.at
```
- **ترتیب:** بر اساسِ `occurred_at`؛ پیامک‌های هم‌دقیقه به ترتیبی که مانده‌هایشان پشتِ هم جور شود
  (`sortForBalance` نسخه‌ی ۱ را نگه دار).
- **ترتیبِ کامل، نه زمان:** زمانِ پیامک فقط تا دقیقه است؛ پس `ledger_math` روی یک **فهرستِ مرتب** از
  تراکنش‌ها و نقطه‌ها کار می‌کند، نه روی مقایسه‌ی زمان. «بعد از C» یعنی «بعد از C در همین فهرست». نقطه‌ی
  **دستی** همیشه بعد از همه‌ی تراکنش‌هایی می‌نشیند که `occurred_at ≤ at` دارند (موجودی‌ای که کاربر «الان»
  می‌گوید همه‌ی آن‌ها را شامل است)؛ نقطه‌ی **بانکی** درست بعد از تراکنشِ خودش.
- **پیامکِ منتظرِ جدیدتر:** اگر پیامکِ `pending`ای مانده‌ای جدیدتر از C دارد، کنارِ موجودی نشان بده:
  «طبقِ آخرین پیامکِ بانک: X (هنوز تأیید نشده)» — عدد را عوض نکن (I1)، فقط نشان بده.
- **موجودیِ اولِ ماه** (برای گزارش) از روی نقطه‌ها **رو به عقب** حساب می‌شود:
  `اولِ ماه = نزدیک‌ترین نقطه‌ی بعد از اولِ ماه − Σ تراکنش‌های بینِ اولِ ماه و آن نقطه`.
  پس کاربر لازم نیست موجودیِ اولِ ماه را بداند؛ «موجودیِ الان» کافی است.

### ۶.۲ ساختِ حساب = لنگرِ موجودی
هنگامِ ساختِ حساب (یا اولین اجرای نسخه‌ی ۲ برای هر حسابِ پیدا‌شده):
«موجودیِ الانِ این حساب چقدر است؟» — پیش‌فرض = مانده‌ی آخرین پیامکِ بانکِ همین حساب («طبقِ پیامکِ ۲ مهر:
۹۴٬۷۶۲٬۲۲۹ — درست است؟»). جواب → یک نقطه‌ی دستی با زمانِ «الان».

### ۶.۳ تشخیصِ اختلاف
برای هر دو نقطه‌ی **پشتِ‌سرِ‌هم** `C1 (t1, b1)` و `C2 (t2, b2)` در یک حساب:
```
انتظار = b1 + Σ علامت‌دارِ تراکنش‌های (t1, t2]      (اگر C2 از یک تراکنش آمده، خودش هم جزوش است)
اختلاف = b2 − انتظار
```
اختلاف ≠ ۰ → یک «پنجره‌ی اختلاف» روی همان حساب با:
- مبلغِ دقیقِ اختلاف و بازه‌ی زمانی (`t1` تا `t2`)؛
- تراکنش‌های داخلِ بازه (شاید یکی مبلغ/نوعش اشتباه است: اختلاف = ۲ برابرِ مبلغ یعنی نوع برعکس)؛
- **پیامک‌های منتظر یا ردشده‌ی داخلِ بازه** — اگر مبلغِ یکی دقیقاً اختلاف را توضیح دهد، پررنگ: «احتمالاً همین
  جاافتاده؛ ثبتش کن» (برای ردشده: «ردش کرده بودی ولی دقیقاً همین اختلاف است؛ [ثبتش کن]» — برگرداندنِ تصمیم هم
  کارِ خودِ کاربر است، پس I2 نمی‌شکند)؛
- دکمه‌ها: **[ثبتِ پیامکِ پیشنهادی] [افزودنِ تراکنشِ جاافتاده] [ویرایشِ یکی از تراکنش‌ها] [ثبتِ «اصلاح»]**.
  «اصلاح» = تراکنشِ `source=adjustment` با یادداشتِ اجباری (کارمزد/سودِ ناشناخته) — **صریح و دیدنی**، هرگز خودکار.
- دو رنگ: **نارنجی** = در بازه پیامکِ منتظر هست (احتمالاً فقط باید تأیید شود؛ طبیعیِ روزهای اول)؛ **قرمز** =
  اختلافِ بی‌توضیح (پیامکِ جاافتاده، کارمزد، یا ورودِ اشتباه).

این همان «راهکارِ تشخیصِ تداخل» است که اشتباهِ دستی را هم می‌گیرد: هر تراکنشِ اشتباه (پیامکی یا دستی) بینِ دو
نقطه‌ی مانده گیر می‌افتد و همان پنجره قرمز می‌شود. اگر کاربر «موجودیِ الان» را اشتباه وارد کند، اولین پیامکِ
بانکیِ بعدی بلافاصله اختلاف نشان می‌دهد («موجودی‌ای که وارد کردی با پیامکِ بانک نمی‌خواند»).

### ۶.۴ حسابِ بی‌پیامک (نقد، حسابِ قدیمی)
فقط نقطه‌های دستی دارد. دکمه‌ی **«تطبیق با موجودیِ واقعی»**: کاربر عددِ واقعی را وارد می‌کند ← نقطه‌ی دستیِ تازه
← اگر با حساب‌شده نخواند، همان پنجره‌ی اختلاف.

### ۶.۵ حسابی که پیگیری نمی‌شود
حسابِ `archived` (مثلاً حسابی که کاربر نمی‌خواهد در دفتر باشد): پیامک‌هایش همچنان `pending` می‌آیند (I1/ت۲)،
ولی پیشنهادشان «تراکنش نیست — حسابِ کنارگذاشته» است و صفحه‌ی منتظرِ تأیید یک دکمه‌ی **«ردِ همه‌ی N پیامکِ حسابِ
کنارگذاشته»** دارد. رد با **یک فشارِ کاربر** است، نه خودکار (بنر هم جدا می‌شمارد تا «۷ منتظر» پر نماند).

### ۶.۶ تکراری
پیشنهادِ «احتمالاً تکراری» (نه حذف): همان متن که بانک دوباره فرستاده، یا تراکنشِ ثبت‌شده با همان حساب/مبلغ/نوع
و (همان مانده، یا ۱۰ دقیقه فاصله). دکمه‌ی «تکراری است» = رد با دلیلِ `duplicate`.

## ۷. صفحه‌ها

1. **خانه:** کارتِ هر حساب (موجودی، زمانِ آخرین نقطه، نشانِ اختلاف)، جمعِ خانواده، درآمد/هزینه‌ی ماه، و بنرِ
   **«۷ پیامکِ منتظرِ تأیید»**.
2. **منتظرِ تأیید:** فهرستِ پیامک‌های `pending` (جدیدترین بالا). هر کارت: متنِ پیامک، پیشنهاد (حساب، نوع، مبلغ،
   زمان، مانده) و دکمه‌های **[ثبت] [ویرایش و ثبت] [تراکنش نیست] [تکراری است]**. کشیدن به راست = ثبت، به چپ
   = تراکنش نیست. **تأییدِ گروهی:** انتخابِ چند کارت + «ثبتِ انتخاب‌شده‌ها» (دکمه‌ی «انتخابِ همه‌ی موارد بی‌مشکل»
   فقط انتخاب می‌کند؛ ثبت همیشه با دستِ کاربر — ت۲).
3. **نوتیفیکیشنِ پیامکِ تازه** با دکمه‌های «ثبت» و «تراکنش نیست» (ثبت با همان پیشنهاد، بدونِ باز کردنِ اپ).
4. **جزئیاتِ حساب:** خط‌زمانِ تراکنش‌ها و نقطه‌های مانده، پنجره‌های اختلاف با دکمه‌های بخشِ ۶.۳، و «تطبیق با موجودیِ واقعی».
5. **برگه‌ی تراکنش:** مبلغ، نوع، حساب، زمان، انتقال، دسته، یادداشت؛ حذف (با تأیید). پیامکِ منبع (فقط خواندنی).
6. **افزودنِ دستی** (همان برگه).
7. **تنظیمات:** تاریخِ شروع (تغییر با هشدار)، فرستنده‌ها، حساب‌ها، خانواده، سلامتِ گوشی‌ها، به‌روزرسانی.
8. **گزارشِ ماه:** موجودیِ اولِ ماه (۶.۱)، درآمد، هزینه، انتقال‌ها، موجودیِ آخرِ ماه، دسته‌ها و بودجه.

## ۸. سرور و همگام‌سازی (ت۳)

- **هر چیزی جز متنِ پیامک** روی سرور است: حساب‌ها (با شماره‌ها، مثلِ کیف‌های امروز)، نقطه‌های مانده، تراکنش‌ها،
  دسته‌ها، **تصمیم‌های پیامک** (`key, content_hash, received_at, status, reject_reason, entry_id` — بدونِ متن و
  فرستنده) و تاریخِ شروعِ هر کاربر.
- مدل‌های تازه: `LedgerAccount` (یا گسترشِ `Wallet`: `archived`)، `Checkpoint`، `Entry` (جدا از `Transaction`ِ
  نسخه‌ی ۱)، `SmsDecision`، و `UserLedgerSettings(start_date)`. همه با شناسه‌ی ساخته‌شده روی گوشی.
- همگام‌سازی: هر مدل «ارسالِ دسته‌ای با نتیجه‌ی هر آیتم» (`upsert_each` موجود) + «دریافت با cursor».
  ویرایش: برنده = `client_updated_at` جدیدتر. حذف: نرم.
- **نصبِ دوباره:** ورود ← دریافتِ همه ← تاریخِ شروع از سرور ← خواندنِ صندوق از تاریخِ شروع ← هر پیامک با
  `SmsDecision` تطبیق (۵.۲): تصمیم‌دار = همان، بقیه `pending`. هیچ چیز دوباره ساخته یا حذف نمی‌شود.
- **خانواده:** هر کس فقط تراکنشِ حساب‌های خودش را می‌نویسد؛ بقیه فقط می‌بینند؛ مدیر همه را می‌بیند. سلامتِ
  گوشی‌ها ساده می‌شود: نسخه، آخرین همگام‌سازی، تعدادِ پیامکِ منتظر، تعدادِ پنجره‌ی اختلاف.
- endpointهای نسخه‌ی ۱ تا وقتی همه‌ی گوشی‌های خانواده به‌روز نشده‌اند (صفحه‌ی سلامت نسخه را نشان می‌دهد)
  می‌مانند؛ بعد حذف.

## ۹. رفتن از نسخه‌ی ۱ به ۲ (اولین اجرا)

1. تاریخِ شروع: از سرور اگر هست؛ وگرنه اولِ ماهِ شمسیِ جاری (و روی سرور ذخیره).
2. حساب‌ها: از کیف‌های موجود + حساب‌هایی که در پیامک‌های این ماه پیدا می‌شود → صفحه‌ی «این حساب‌ها را پیدا
   کردیم؛ موجودیِ الانِ هر کدام؟» (پیش‌فرض = آخرین مانده‌ی بانکی؛ ۶.۲).
3. پیامک‌های از تاریخِ شروع → `sms_items` با `pending`. **دسته‌بندیِ** تراکنشِ نسخه‌ی ۱ با همان اثرانگشت در
   برگه‌ی ثبت پیش‌پر می‌شود (کاربر دوباره دسته نزند).
4. جدول‌های نسخه‌ی ۱ یک نسخه **فقط‌خواندنی** می‌مانند (برای برگشت)، نسخه‌ی بعد حذف.
5. پرچمِ `ledger_v2` در تنظیمات: تا پایانِ فازِ ۳ اپ با پرچم بین ۱ و ۲ جابه‌جا می‌شود (توسعه روی `main`).

## ۱۲. سناریوهای پذیرش (هر کدام تستِ خودکار؛ ۳ به بعد روی گوشی هم)

هسته:
1. **نصبِ وسطِ ماه:** تاریخِ شروع = اولِ ماه؛ پیامکِ ماهِ قبل هیچ‌جا نیست؛ پیامک‌های این ماه همه `pending`.
2. **ثبتِ همه:** موجودیِ حساب = مانده‌ی آخرین پیامکِ بانک؛ هیچ پنجره‌ی اختلافی نیست.
3. **رد کردنِ یک پیامکِ واقعی:** پنجره‌ی اختلاف دقیقاً بینِ دو پیامکِ اطرافش با همان مبلغ؛ همان پیامکِ ردشده با
   «ردش کرده بودی ولی دقیقاً همین اختلاف است» پیشنهاد می‌شود (تصمیم خودکار عوض نمی‌شود)؛ ثبتش ← اختلاف صفر.
4. **مبلغِ دستیِ اشتباه:** اختلاف در همان پنجره؛ ویرایشِ مبلغ ← صفر. **نوعِ برعکس:** اختلاف = ۲ برابرِ مبلغ و
   پیشنهادِ «نوع برعکس است».
5. **حسابِ بی‌پیامک:** لنگرِ ۱۰م، هزینه‌ی دستیِ ۱م ← ۹م؛ تطبیق با ۸٫۵م ← اختلافِ ۰٫۵م ← «اصلاح» با یادداشت ← صفر.
6. **موجودیِ الانِ اشتباه:** لنگرِ اشتباه ← اولین پیامکِ بانکیِ بعدی اختلاف نشان می‌دهد.
7. **نصبِ دوباره:** حذف و نصب ← حساب‌ها، تراکنش‌ها، دسته‌ها، نقطه‌ها، تصمیم‌ها و تاریخِ شروع عیناً؛ فقط پیامکِ تازه منتظر.
8. **به‌روزرسانی از ۱٫۰٫x:** هیچ تراکنشی خودکار ساخته نمی‌شود؛ دسته‌های قبلی در برگه‌ی ثبت پیش‌پر.
9. **پارسرِ بهتر:** تراکنش‌های ثبت‌شده و تصمیم‌ها دست‌نخورده؛ فقط پیشنهادِ `pending`ها عوض می‌شود.
10. **پیامکِ زنده + صندوق:** یک پیامک، یک ردیف (قاعده‌ی ۱۰ دقیقه).
11. **بانک همان پیامک را دوباره می‌فرستد:** دومی «احتمالاً تکراری»، تصمیم با کاربر.
12. **اعتبارِ دیجی‌پی/دیما:** پیشنهادِ «تراکنش نیست»؛ فقط اگر کاربر ثبت کند و حساب بدهد، شمرده می‌شود.
13. **پاسارگادِ دیجیتال (کارمزد/وام/قسطِ بی‌شماره):** حسابِ پیشنهادی = تنها حسابِ پاسارگاد یا حسابی که مانده‌اش
    جور است؛ قسطِ بی‌مانده در پنجره‌ی اختلافِ هم‌مبلغ پررنگ پیشنهاد می‌شود. (نمونه‌ها: fixtureهای `real_format_pasargad_*`.)
14. **حریمِ خصوصی:** هیچ payloadی به سرور متن یا فرستنده‌ی پیامک ندارد (تستِ موجودِ `test/security/` گسترش یابد).
15. **دو عضو:** هر کس فقط حساب‌های خودش را می‌نویسد؛ مدیر همه را می‌بیند.

## ۱۳. چیزهایی که عمداً نداریم

- پردازشِ پیامک‌های قبل از تاریخِ شروع (I4). - «موجودی» که از جمعِ همه‌ی تاریخچه ساخته شود (مبنا = نقطه‌ها؛ ت۴).
